# 파이프라인 생성 테스트와 수기 테스트 비교

기존 수기 테스트는 Gen·Critique·Eval·Validate가 끝난 후에만 열어 비교했다.

| 비교 항목 | 사람이 작성한 A-3·A-4 | 파이프라인 생성 결과 |
|---|---|---|
| 정상 할인 | 정률·정액, 최종 금액 검증 | 동일 |
| 입력 실패 | 빈 코드·비로그인·미존재·만료 | 동일, DB 미호출까지 JSON 요구사항에 연결 |
| 경계값 | 최소금액 동일/1원 미달, 정률 최대 한도 | 동일 + 정액 최대 한도 2,000원/0원 추가 |
| 사용 한도 | 사용자 한도 도달 거절 | 동일 |
| Mock | Supabase만 Mock, 실제 할인 계산 사용 | 동일 원칙을 계약 게이트로 강제 |
| 주문 부수효과 | PG 금액 불일치, 결제 거절, 저장·다운로드 권한 | 사람이 더 구체적 |
| 추적성 | 설명과 파일 경로 중심 | 모든 테스트에 `test_id`·`requirement_id` 연결 |
| BDD 격리 | Cucumber World/Fake 구현 | 새 World·fake 생성 자체를 테스트로 관찰 |
| items 신뢰 경계 | 보조 실험에서 subtotal 조작 문제 발견 | 정식 Vitest·Gherkin 회귀 테스트로 승격 |

## 둘 다 찾은 것

- 정률·정액 할인과 상품가 하한
- 빈 코드·비로그인 시 DB를 호출하지 않는 규칙
- 존재하지 않는 쿠폰, 만료 쿠폰, 사용자 사용 한도
- 최소 주문금액과 같으면 통과하고 1원 부족하면 거절하는 경계값 쌍
- 외부 I/O만 가짜로 만들고 핵심 도메인 계산은 실제로 실행하는 원칙

## 사람이 더 잘한 것

- PG 승인 금액 불일치, 승인 거절, 다운로드 권한처럼 실제 주문 결과의 부수효과를 구체적으로 검증했다.
- 실제 코드와 운영 맥락을 바탕으로 `maximum_discount=0` 정률 결함을 먼저 발견했다.
- A-4 보조 실험에서 `items`와 `subtotal`을 일부러 어긋나게 해 보안상 의미를 설명했다.

## 파이프라인이 추가로 찾은 것

- 정액 쿠폰의 maximum_discount 정책이 요구사항과 구현에서 일치하지 않는다는 새 질문을 만들었다.
- A-4 보조 실험에 머물던 items 우선 규칙을 정식 단위·Gherkin 회귀 테스트로 바꿨다.
- 메타데이터에만 있고 실행 파일에는 빠진 시나리오, Step Definition 누락, 숨은 World 기본값을 반복 과정에서 잡았다.

## 파이프라인의 거짓 양성 위험

- `REQ-A3-CAP` 문장이 쿠폰 종류를 제한하지 않아 정액에도 한도가 적용된다고 해석했다. 실제 정책이 정률 전용이면 AI가 만든 Red는 제품 버그가 아니라 요구사항 해석 오류다.
- A-4 하위 API는 전달받은 `items` 합계를 우선할 뿐 그 값이 서버 DB에서 왔는지는 증명하지 못한다. 그런데 Eval은 이를 5점으로 통과시켰다.

따라서 AI 테스트 생성의 가치는 테스트 수를 늘리는 데 있지 않다. 사람이 놓친 가설을 넓게 만든 뒤, 실행 결과와 도메인 정책으로 참·거짓을 다시 판정하는 데 있다.
